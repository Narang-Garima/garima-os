ANALYTICAL PRINCIPLES

The ideas I apply when designing and reviewing data systems.

Question the data first

I profile and validate before I model. Bad data upstream silently corrupts every insight downstream — find it early.

Measure business impact, not just accuracy

A model with 92% accuracy that nobody uses is a failure. I measure outcomes in revenue, decisions, and operational change.

Build for the decision-maker

Dashboards exist to drive decisions, not to demonstrate technical skill. I design with the stakeholder's question in mind first.

Reliability before complexity

A simple pipeline that runs every day beats a sophisticated one that fails on Mondays. I ship things that teams can actually depend on.

Document Portal — Enterprise RAG System_

A production RAG platform that turns any document into something you can query with natural language. Built with the same Azure-first approach used at OpenText: cascading extraction, hybrid retrieval, and per-user workspace isolation.

GitHub
28 test cases
10-case DeepEval RAG quality suite
TECH STACK
FastAPILangChainChromaDBBM25 Gemini VisionDockerGitHub ActionsAWS ECS
DATA ENGINEERING HIGHLIGHTS
Hybrid vector + BM25 retrieval with auto-weighted RRF reranking for high-precision document search
8 document formats supported via cascading extraction with format-specific fallback logic
Per-user workspace isolation — persistent session context without data leakage across users
Full CI/CD: GitHub Actions → Docker build → AWS ECS/Fargate production deployment
CONTEXT

The Problem_

Enterprise teams drown in documents. PDFs of contracts, Excel reports, SQL data exports, Word specs — all searchable only by Ctrl+F or human memory. I wanted to build the same kind of semantic search infrastructure I had access to at OpenText, but open-source, portable, and actually deployable by a solo engineer.

CONSTRAINTS

Data Challenges_

  • Mixed document formats with wildly different extraction complexity (scanned PDFs vs structured XLSX)
  • Maintaining retrieval quality across 8 formats without format-specific tuning for each
  • Per-user isolation without a full auth system adding overhead
  • Evaluating RAG quality rigorously — not just "does it return something"
DECISIONS

Engineering Decisions_

  • Chose BM25 + vector hybrid over pure semantic — keyword matches matter for exact terminology in enterprise docs
  • RRF reranking auto-weights across retrieval methods — no manual tuning per document type
  • Gemini Vision for scanned PDFs — handles image-based content that text parsers miss
  • DeepEval for RAG evaluation — faithfulness, relevance, and context precision as first-class metrics
EVOLUTION

Next Steps_

  • Add Azure AI Search as a production vector store option alongside ChromaDB
  • Fine-tune chunk size strategy per document type based on evaluation results
  • Add conversation memory for multi-turn querying across sessions
  • Extend to Snowflake and live SQL data sources for real-time enterprise queries

Learning Lab_

End-to-end Agentic AI · Strands SDK · Hands-on Design Doc Generator

🧠

What is Agentic AI?

❌ Traditional AI
user → prompt
model → response
DONE. (one shot)
✅ Agentic AI
user → GOAL
agent → think()
agent → pick_tool()
agent → run_tool()
agent → observe()
→ loops until done

The key shift: Instead of answering a single question, an Agentic AI has a goal, a set of tools (skills), and an autonomous loop — it decides how to accomplish the goal by calling tools in sequence, observing results, and adapting its plan. This is exactly how humans work on complex projects.

⚙️

Strands SDK — System Architecture

Strands Agents is AWS's open-source Python SDK for building agentic systems. Three concepts power everything:

📜
System Prompt
The agent's personality, role, rules, and output format.
🔧
Tools (Skills)
Python functions with @tool decorator. The LLM can call these.
🔄
ReAct Loop
Reason → Act → Observe — keeps running until the goal is met.
Architecture Diagram
User Input (requirements text + config)
          │
          ▼
  ┌──────────────────────────────────────────────┐
  │            Strands Agent                      │
  │  system_prompt: "You are DesignDocAgent..."   │
  │  model: Claude 3.5 Sonnet (AWS Bedrock)       │
  │                                               │
  │  ┌─────────────────────────────────────────┐  │
  │  │         ReAct Loop                      │  │
  │  │  while goal_not_done:                   │  │
  │  │    thought = llm.think(history+tools)   │  │
  │  │    tool    = thought.pick_tool()        │  │
  │  │    result  = execute(tool, args)        │  │
  │  │    history.append(result)               │  │
  │  └─────────────────────────────────────────┘  │
  └──────────────────────────────────────────────┘
          │
          │  calls one of:
          ├──▶ parse_requirements()    → structured JSON
          ├──▶ generate_sections()     → Markdown sections
          ├──▶ update_config()         → new config dict
          ├──▶ refine_output()         → updated section
          └──▶ export_document()       → .md file
          │
          ▼
    Design Document (10 structured sections)

Code Walkthrough — Key Concepts

# agent.py — The system prompt is the agent's "soul"
# It defines: role, tools it has, output format, rules

SYSTEM_PROMPT = """
You are DesignDocAgent — a senior software architect.

YOUR MISSION:
  Given a requirements doc + config, produce a structured
  Software Design Document (SDD).

YOUR SKILLS (tools you can call):
  1. parse_requirements   — extract structure from raw text
  2. generate_sections    — write each doc section
  3. update_config        — apply config changes
  4. refine_output        — edit sections interactively
  5. export_document      — write final .md file

OUTPUT FORMAT:
  ## 1. Executive Summary
  ## 2. Problem Statement
  ## 3. System Architecture
  ... (10 sections total)

RULES:
  • If requirements are vague → ask clarifying questions
  • If config changes → regenerate only affected sections
  • Always end with: "✓ Doc ready. What to change?"
"""
# A @tool is just a Python function.
# The docstring IS the description the LLM sees.
# The LLM reads it and decides WHEN to call this function.

from strands import tool

@tool
def parse_requirements(requirements_text: str) -> dict:
    """
    Parse a requirements document and extract structured fields:
    project name, stakeholders, functional requirements,
    non-functional requirements, tech stack, and timeline.

    Args:
        requirements_text: Raw text of the requirements document
    Returns:
        A structured dictionary with parsed fields
    """
    # Your Python logic here
    parsed = {
        "project_name": extract_project_name(requirements_text),
        "functional_requirements": extract_bullets(requirements_text),
        "tech_stack": extract_tech(requirements_text),
    }
    return parsed  # Agent sees this as the "observation"
from strands import Agent
from strands.models import BedrockModel

# Create the model (Claude 3.5 via AWS Bedrock)
model = BedrockModel(
    model_id="claude-3-5-sonnet-20241022",
    region_name="us-east-1",
    streaming=True  # stream agent thoughts in real time
)

# Build the agent — attach system_prompt + all 5 tools
agent = Agent(
    system_prompt=SYSTEM_PROMPT,
    tools=[
        parse_requirements,   # @tool functions
        generate_sections,
        update_config,
        refine_output,
        export_document
    ],
    model=model,
)

# Use the agent — it autonomously decides which tools to call
result = agent("Generate a design doc for: AI Customer Support Bot")
# → agent thinks → calls parse_requirements → calls generate_sections → done
# What Strands does internally (simplified)
# This is the ReAct (Reason + Act) loop

def react_loop(goal: str):
    history = [system_prompt, user_message(goal)]
    
    while True:
        # REASON: LLM decides what to do next
        thought = llm.complete(history + tool_descriptions)
        
        if thought.is_final_answer:
            return thought.content   # ✓ Goal achieved
        
        # ACT: Execute the chosen tool
        tool_name = thought.tool_call.name
        tool_args = thought.tool_call.arguments
        result    = tools[tool_name](**tool_args)
        
        # OBSERVE: Add result to history, loop again
        history.append(tool_result(tool_name, result))
        
        # Example trace for our agent:
        # Turn 1: Think → call parse_requirements(req_text)
        # Turn 2: Think → call generate_sections(parsed, config)
        # Turn 3: Think → "I have all sections, doc is ready"
        # → returns final document
